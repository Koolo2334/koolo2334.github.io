## 作品紹介

「グラフィックの力で、プレイヤーの興奮を最大化する」エンジニアを目指し、最新の API を用いた描画アーキテクチャを自分の手で設計するために制作しているゲームエンジンです。

「柔軟性が高く、使いやすい」をコンセプトに、描画基盤からエディタ、ゲームの実行までを設計・実装しました。このエンジンでパズルゲーム「Luvia」も制作しています。

## 課題と解決

<Case n="01" title="ゲームごとに異なる描画を、柔軟に組み替えたい">
  <Fragment slot="problem">
    求める描画はゲームによって異なります。パスを追加・変更するたびにリソースの寿命やバリアを手で管理する構成では、表現を試すたびに修正範囲が広がってしまいます。
  </Fragment>

  **RenderGraph** を採用しました。各パスが使うリソースを宣言するだけで、寿命の解析、メモリの重ね置き、バリアの挿入を自動で行います。パイプラインを変更せずに描画を差し込める `IRenderFeature` も用意しました。

  <Flow
    cols={[
      { label: 'IRenderPipeline', items: ['Shadow', 'GBuffer', 'Lighting', { text: '+ IRenderFeature', sub: '外から描画を差し込む', hot: true }, 'Translucent', 'PostProcess'] },
      { label: 'RenderGraph', items: [{ text: '寿命の解析', sub: 'いつ作り、いつ捨てるか' }, { text: 'メモリの重ね置き', sub: '寿命が重ならない資源で共有' }, { text: 'バリアの自動挿入', sub: '状態遷移を自動で記録' }] },
      { label: 'GPU', items: ['CommandList'] },
    ]}
    arrows={['リソースを宣言', '実行']}
    caption="Engine.Graphics.RenderGraph.ixx"
  />

  <Fragment slot="result">
    描画パスの追加・入れ替えが容易になり、Luvia の光の表現もエンジン側を変更せずに実装できました。
  </Fragment>
</Case>

<Case n="02" title="大量のテクスチャを扱う描画で、リソース管理が煩雑になった">
  <Fragment slot="problem">
    従来のディスクリプタ管理では、描画ごとにテーブルを用意して切り替える必要がありました。大量の SRV を動的に扱う複雑な描画を実装するにつれ、開発効率と処理効率の両方が悪化していました。
  </Fragment>

  **Bindless アーキテクチャ** を採用し、すべての SRV を単一の DescriptorTable に格納して、シェーダからインデックスで参照する形にしました。

  <Bindless />

  <Fragment slot="result">
    テーブルの切り替えが不要になり、シェーダはインデックスを受け取るだけで任意のテクスチャを参照できるようになりました。
  </Fragment>
</Case>

<Case n="03" title="PBR と NPR を、1つのパイプラインで共存させたい">
  <Fragment slot="problem">
    マテリアルごとにシェーダを個別に書く方式では、描画パスが増えるほど組み合わせの管理が難しくなります。

  **動的シェーダコンパイル** を実装しました。マテリアル固有の HLSLI を各描画パスのシェーダへ自動で展開し、ライティングはシェーディングモデルの ID で切り替えます。ビルド時には全順列を事前コンパイルします。

  <Fragment slot="result">
    HLSLI を登録するだけでシェーディングモデルを追加でき、キャラクター用の前方描画と合わせて PBR と NPR を共存させました。
  </Fragment>
</Case>

<Case n="05" title="ビルドと再起動の待ち時間が、ゲーム制作の妨げになった">
  <Fragment slot="problem">
    コードを変更するたびにビルドとエディタの再起動が必要で、試行錯誤のテンポが落ちていました。
  </Fragment>

  C++20 の **Modules** を採用してコンパイル時間を短縮しました。さらにエンジンを1つの DLL にまとめ、ゲームのコードを別の DLL に分けることで、エディタを開いたままゲームの DLL を差し替える **ホットリロード** を実装しました。

  <Flow
    cols={[

  <Fragment slot="result">

  </Fragment>
</Case>

## エディタとゲーム制作

アセットの種類ごとに専用のエディタを用意し、マテリアルはノードを繋ぐだけでシェーダが生成されます。

<Gallery items={[
  { src: materialEditor, caption: 'マテリアルエディタ' },
  { src: uiDesigner, caption: 'UI デザイナー' },
  { src: curveEditor, caption: 'カーブエディタ' },
  { src: controlPanel, caption: 'コントロールパネル' },

ゲームのコードは EnTT による ECS で記述します。コンポーネントの宣言の下にマクロを書くだけでリフレクションに登録され、保存・詳細パネル・Undo などのエンジン機能をそのまま利用できます。

```cpp
struct FirstPersonComponent {
    float WalkSpeed = 4.5f;
    float JumpSpeed = 5.0f;
};
RADX_COMPONENT(FirstPersonComponent, "FirstPerson",
    RADX_FIELD(WalkSpeed).Range(0.0f, 20.0f),
    RADX_FIELD(JumpSpeed).Range(0.0f, 20.0f));
```
